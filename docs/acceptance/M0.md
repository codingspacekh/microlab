## Decision

1. **Engine:** the official MicroPython WebAssembly port in a module worker, version pinned. R1 does **not** fail.
2. **`time`, sleep and ticks:** our own module put into `sys.modules` before the student's code; sleeping is
   `Atomics.wait` on the shared *control* word, so it uses no CPU and Stop or an input change wakes it at once.
3. **Stop (N-03 ≤ 0.5 s):** set the stop flag → `KeyboardInterrupt` from the next bridge call or line hook (0–10 ms);
   if Python hasn't stopped after **200 ms**, end the worker and start a fresh one (21 ms). Both are within budget.
4. **Own build — recommended, to be proven before M2:** the npm build has no VM hook into JavaScript, so a program
   stuck in `while True: pass` can't be interrupted from inside and — more important — **a button's IRQ handler
   would never run** during it (N-01: on the real board it does). Our own build of the same MicroPython version adds
   one small hook (`MICROPY_VM_HOOK_POLL` → a JS function that checks the stop flag and pending pin IRQs every few
   hundred bytecodes) and keeps `settrace` for the line marker. It is built with Emscripten in Docker by a script in
   `scripts/`, from a pinned MicroPython tag, and the `.wasm` + `.mjs` are kept in the repo so nobody needs Emscripten
   to work on MicroLab.
   *To prove:* the hook interrupts `while True: pass`, runs a scheduled IRQ handler, and costs < 20 % speed.
   **Waiting for:** Docker Desktop running on this Mac (it is installed but not started).
5. If the own build fails, the fallback is the npm `settrace` build + ending the worker on Stop, and IRQs delivered
   only at bridge calls and line events (documented as a limit: `while True: pass` must become
   `while True: time.sleep_ms(10)`, which the Learn pages would then teach).
