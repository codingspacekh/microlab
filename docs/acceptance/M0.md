## Decision

1. **Engine:** the official MicroPython WebAssembly port in a module worker, version pinned. R1 does **not** fail.
2. **`time`, sleep and ticks:** our own module put into `sys.modules` before the student's code; sleeping is
   `Atomics.wait` on the shared *control* word, so it uses no CPU and Stop or an input change wakes it at once.
3. **Stop (N-03 ≤ 0.5 s):** set the stop flag → `KeyboardInterrupt` from the next bridge call or line hook (0–10 ms);
   if Python hasn't stopped after **200 ms**, end the worker and start a fresh one (21 ms). Both are within budget.
4. **Own build — decided, proven 2026-11-05 (see *Own build — results*):** the npm build has no VM hook into JavaScript, so a program
   stuck in `while True: pass` can't be interrupted from inside and — more important — **a button's IRQ handler
   would never run** during it (N-01: on the real board it does). Our own build of the same MicroPython version adds
   one small hook (`MICROPY_VM_HOOK_POLL` → a JS function that checks the stop flag and pending pin IRQs every few
   hundred bytecodes) and keeps `settrace` for the line marker. It is built with Emscripten in Docker by a script in
   `scripts/`, from a pinned MicroPython tag, and the `.wasm` + `.mjs` are kept in the repo so nobody needs Emscripten
   to work on MicroLab.
   *Proven:* the hook interrupts `while True: pass` (3 ms), runs a scheduled IRQ handler during it, `settrace`
   works, and it costs **no** speed (1 M loop 486 ms; npm 520 ms). It is built **without ASYNCIFY**: binaryen's
   `--spill-pointers` pass lets the garbage collector run safely while a program runs, synchronously.
   Files and versions: [`vendor/micropython/README.md`](../../vendor/micropython/README.md).
5. *(Not needed — kept for the record.)* If the own build had failed, the fallback was the npm `settrace` build + ending the worker on Stop, and IRQs delivered
   only at bridge calls and line events (documented as a limit: `while True: pass` must become
   `while True: time.sleep_ms(10)`, which the Learn pages would then teach).

## Own build — results (2026-11-05)

`scripts/build-micropython.sh` builds MicroPython v1.29.0 with Emscripten 6.0.13 in Docker (Colima on this Mac), with
our variant `vendor/micropython/variant/microlab/` (based on *standard*: VM hook every 64 jumps → `Module.microlabHook`,
`sys.settrace` on, no extra frozen libraries) and a small patch (`vendor/micropython/microlab.patch`: `library.js`
calls our hook; `main.c` skips the register scan). The built `.mjs` + `.wasm` are in the repo.

**The garbage collector was the hard part.** Three builds were tried:

| Build | Result |
|---|---|
| 1. No ASYNCIFY, upstream GC | ❌ aborts at the first collection: `emscripten_scan_registers` needs ASYNCIFY |
| 2. ASYNCIFY (as upstream's *standard*) | works only if the program is started with an asyncify-aware call: each collection **returns to JavaScript** (unwind, `setTimeout(0)`, rewind) in the middle of the student's program — a plain `runPython` aborts. ~70 % slower (1 M loop ~1 040 ms), and a collection inside a JS → Python callback would abort (it can't unwind through JavaScript) |
| 3. **No ASYNCIFY + binaryen `--spill-pointers`**, stack-only scan — **chosen** | pointer locals are kept on the C stack, so the stack scan finds them; synchronous; same speed as npm |

(GC_SPLIT_HEAP_AUTO, as in the npm *pyscript* build, was ruled out: it never collects while a program runs, so a
`while True:` that makes strings would grow memory until Stop.)

Build 3, `node spikes/micropython-worker/hook-spike.mjs` and `gc-spike.mjs` (fresh interpreter per test):

| Check | Result |
|---|---|
| Load | 16 ms; `.wasm` 603 KB (name section kept, needed by the pass) |
| Stop `while True: pass` · `while True: x += 1` · two-line loop | `KeyboardInterrupt` in 3 · 52 · 36 ms ✅ |
| A pin IRQ (scheduled with `micropython.schedule` from the hook) during `while True` | handler ran 3 times, loop ended ✅ |
| `settrace` lines | 1, 2, 3 ✅ |
| 1 M-iteration loop (big ints, so it collects) | **486 ms** — npm 520 ms plain, 567 ms settrace ✅ |
| 200 k iterations making strings and lists, 256 KB heap | memory stays bounded (≤ 250 KB used), 655 ms ✅ |
| 3 000 survivors among garbage, many collections | 0 corrupted ✅ |
| Objects held only by C while Python runs in them (`list(map(f))`, `sorted(key=)`, `join` of a generator, comprehensions), 5 rounds, 1 MB heap | 20 of 20 correct ✅ — the same `MemoryError` as build 2 at 256 KB: a genuine out-of-memory (one contiguous block needed), as on a board |
| Stop in an allocating `while True:` | `KeyboardInterrupt` ✅ |
| Modules | `pathlib`, `unittest`, `logging` not there (as on the boards) ✅; `js` / `jsffi` still there — remove in M2 |

For M2: the worker runs the program synchronously (a plain `runPython` works) and always sets
`Module.microlabHook` (with none set, the patch falls back to upstream's slower Node interrupt check). With no
ASYNCIFY, the hook may call into Python, e.g. `micropython.schedule` for an IRQ handler, as the spike does.
