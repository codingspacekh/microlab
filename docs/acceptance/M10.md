## Findings carried in from the design

1. **The Pico and Pico W have no power light** — the helper's cable test for them is the BOOTSEL drive (requirements
   Rev 8, screen 14).
2. **macOS asks before an app may write to a removable drive** (`RPI-RP2`, `MICROBIT`): seen when the Pico W was
   updated; installing MicroPython says so first (Rev 8, screen 14b).
3. With no data on USB at all (a charge-only cable, or a board not plugged in), nothing appears in the port list *or*
   in `ioreg` — the Pico W before it was plugged in properly looked exactly like that.
4. *(1)* **`serialport` 13** lists the ports in the main process; its prebuilt N-API binaries load in Electron 45 with
   no rebuild (checked: the built app found the teacher's Pico W). On macOS it lists `/dev/tty.*`; the board is
   opened through `/dev/cu.*` (the `tty` side waits for a carrier signal these boards never give).
5. *(1)* **USB can't tell a Pico from a Pico W, nor a micro:bit V1 from a V2**: until the board answers (M10.2) the
   chip says "Pico" and a Pico fits a Pico W project.
6. *(1)* **Fixtures**: `mac-pico-w.json` is recorded with `serialport` on the teacher's Mac; `mac-microbit.json`,
   `mac-pico-bootsel.json` and `mac-no-board.json` are rebuilt from what was seen on the same Mac with `mpremote`, `ioreg`
   and `/Volumes` (re-record with `serialport`); the Windows and CH340 lists are *constructed* from serialport's
   documented output and say so — the manual matrix replaces them with real recordings.
7. *(1)* **Windows drive labels** (a Pico in BOOTSEL there) are read when installing MicroPython is built (M10.7);
   on Windows the watcher sees ports only until then.
8. *(2)* **Recorded on the teacher's Pico W** (`tests/fixtures/repl/pico-w-idle.json`, `pico-w-running.json`): the
   exchange of a check, idle at `>>>` and with its `main.py` running. The teacher's program catches Ctrl-C and prints
   "stopping"; after the soft reset it starts again ("Joining 'CHAMPIONCODERS' …"). The built app asked the real board
   in **252 ms**.
9. *(2)* **Ctrl-D in the raw REPL does not run `main.py`**; Ctrl-B first, then Ctrl-D at the normal prompt does — that
   is how the check gives the board its program back (R10).
10. *(2)* **A held port**: `serialport` locks the port, so a second program gets "Cannot lock port" (macOS, Linux) or
   "Access denied" (Windows). Tried on the real Pico W with another process holding it: *Pico · used by another
   program*, then **Try again** after it let go: *Pico W · MicroPython 1.29*. `lsof` + `ps` name Thonny, the Arduino
   IDE, Mu, mpremote, another MicroLab; Windows can't tell without admin rights, so there it is "another program".
11. *(2)* **R10 kept**: only a board *plugged in* is asked by itself; one already there when MicroLab starts may be
   running something the student is watching, so its card offers **Check the board** ("its program stops for a moment
   and starts again") — a button not in the approved screens, for the teacher to check. Send to board (slice 3) asks
   the board anyway.
12. *(2)* **Still to record on the micro:bit**: its banner and its soft-reboot words (the check doesn't need either: a
   restart worded otherwise still counts). Also on ESP32: whether opening its port restarts it (DTR/RTS, R10).
13. *(3)* **The board's file helpers are tested on MicroPython itself** (MicroLab's own build, as the Pico W and as
   the micro:bit), and `FakeBoard` does the same calls natively — so the file tests stay fast and the Python they
   rely on is real.
14. *(3)* **The micro:bit**: no folders, no `os.rename` and (we expect) no `hashlib` — files are compared by reading
   them back and put in place by copying on the board; a file in a folder is refused before anything is written.
   *To confirm on the teacher's micro:bit:* `hashlib` and `os.stat` there.
15. *(3)* Screen 08's boards are radio rows (our own controls, N-14) rather than cards; its *Print the wiring list* and
   driver guide links wait for those features (the connection helper is slice 6). *Remove other files* (F-50) comes
   with Board files (slice 5), where the student sees what would go. The board's console after a send is slice 4.
16. *(3)* In fake-USB mode (the tests) the old `main.py` is kept in the test's own folder, never the user's Documents.
17. *(3)* **Sent to the teacher's Pico W from the built app** (2026-11-06, with the teacher's go-ahead): a new Pico W
   project's Blink → *Send and run*, *Keep a copy* on — **1.9 s**; "Sent to the Pico W: main.py (0.2 KB)"; the board
   restarted and ran it (Ctrl-C then stopped it at `main.py` line 9, its `time.sleep`). Every file's SHA-256 before and
   after: of 43 files only `main.py` changed, no `.mlab-part` left. The copy kept in *Board backups* had the old
   `main.py`'s SHA-256 (`6fbdf15f…`, as the backup of the morning). The teacher's `main.py` (12.5 KB) was then sent
   back **through MicroLab's own Send**: all 43 files matched the first snapshot again, and the board's program ran
   ("Joining 'CHAMPIONCODERS' …"). — Files copied both ways match by checksum (gate 3): ✅ on the Pico W.
18. *(3, bug found by the teacher)* **"The board stopped answering"** on a send to the Pico W, with *Keep a copy* on.
   Cause: reading back the teacher's 12.5 KB `main.py` took **971 ms** on the board (each byte formatted in Python),
   and every answer had 1 s in all. Fixed: (a) the wait is for *silence* — an answer that keeps coming is waited for
   however long it takes, a board quiet for 5 s on a file command (1 s otherwise) times out; (b) reading back uses
   the board's `binascii.hexlify` where there is one — **69 ms** for the same file. Regression tests: a FakeBoard
   that answers a line at a time (`pace`), and one that goes quiet mid-answer (`stallAfter`); the Python way without
   `binascii` checked on MicroPython. On the real board the same send then took 0.9 s; the teacher's `main.py` was
   sent back and all 43 files matched the snapshot again. The board was never left changed: the failed send had
   stopped before writing anything.
19. *(3, bug found by the teacher on the micro:bit)* **The first send worked, later ones didn't.** Reproduced with six
   sends in a row: one failed with "NameError: name 've' isn't defined" — **bytes of the 1.3 KB helper code were
   lost** on the way in: the micro:bit's serial input (through its interface chip) can't always keep up with a
   plain raw-REPL command, and the board then saw broken Python (or, with the final Ctrl-D lost, waited for ever:
   "the board stopped answering"). The Pico W's native USB has flow control and never showed it. Fixed as
   mpremote and Thonny do: commands of 64 bytes or more go in **raw-paste mode** (MicroPython 1.14+; the micro:bit
   answered `R\x01` with a window of 128) — the board asks for the command a window at a time; firmware that
   refuses it or doesn't know it gets the plain raw REPL. Short commands stay plain, as recorded. FakeBoard now has
   raw-paste, and a `lossy` input that drops what comes too fast (the bug, staged: without raw-paste the long
   command fails, with it it arrives whole). On the teacher's micro:bit: **16 sends of 1 / 16 failed → 16 / 16**
   (main.py 170–742 bytes, 1.0–1.7 s each, the old one kept each time); its `main.py` (the heart starter) put back
   and checked byte for byte; its check recorded (`tests/fixtures/repl/microbit-running.json`).
20. *(3)* **On the micro:bit**: `os` has `remove`, `stat`, `listdir`, `ilistdir`, `size` — no `rename`, `mkdir`,
   `statvfs`; **no `hashlib`, no `binascii`** (files are compared by reading them back, the slow way). Its banner is
   "MicroPython v1.18 on 2023-10-30; micro:bit v2.1.2 with nRF52833"; it restarts with "MPY: soft reboot"; it keeps
   what came with the Ctrl-C that stopped its program. `mpremote fs ls` shows its files as 0 bytes (`ilistdir`
   gives no size there) — `os.stat` has the right size.
21. *(3)* **A kept copy's folder was named "micro:bit 2026-…"** — fine on macOS, refused by Windows: now
   "micro-bit 2026-…" (`backupFolder`, tested).
22. *(3)* Raw-paste on the Pico W is to be tried when it is plugged in again (it has MicroPython 1.29; the same
   protocol).
23. *(4)* **Recorded on the teacher's micro:bit**: at `>>>` it echoes what is typed and answers (`1+1` → `2`); after
   a line ending in `:` it indents the next line itself, and Enter on that indent does not end the block — so a
   block typed in the console goes in **paste mode** (Ctrl-E … Ctrl-D: "paste mode; Ctrl-C to cancel, Ctrl-D to
   finish", each line echoed after "=== "), shown as `...` lines. Its echo comes in pieces (`\r\n=` then `== `):
   the first try on the real board showed `===`; the console now holds back what may be the start of one, and
   FakeBoard sends it in pieces too (the test went red, then green).
24. *(4)* **Tried on the teacher's micro:bit** through the built app, changing none of its files: Open the
   console → Stop → `1+1` → `2`; a `for` block → `count 0` … `count 2`; `nope` → its NameError in red; *Run main.py
   on the board* (the heart starter from the editor) running until Ctrl+C; Restart → "MPY: soft reboot" and the
   teacher's program again; Let go. Its `main.py` (the teacher's own, 429 bytes) was byte for byte the same after.
25. *(4)* Two buttons were both called "Stop" (the simulator's and the board's): the board's is now *Stop the
   board's program*, the banner's *Stop the board*.
26. *(4)* Runs of the whole suite at a load average over 100 (another project's Electron tests running at the same
   time on the teacher's Mac) time tests out at 5 s that pass alone and pass again when the machine is quiet; not a
   fault of these slices.
