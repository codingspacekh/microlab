## Findings and decisions

1. **Board behaviour after an error, copied from the ports' `main.c`:** an error in `boot.py` is printed and
   `main.py` still runs; `sys.exit()` ends quietly; `boot.py` and `main.py` share one namespace (the REPL's).
2. **errno numbers.** MicroPython's `VfsPosix` passes on the WebAssembly C library's numbers (ENOENT = 44). The
   boards use the usual ones, and students see them (`OSError: [Errno 2] ENOENT`), so `open` and the file
   functions of `os` go through `src/python/common/_os.py`, which maps them. Its frames are hidden from tracebacks.
3. **The file system.** Python's `/` is the project's folder (a `VfsPosix` mounted at `/`), so `os.listdir('/')`
   shows the project's files only, and `/tmp`, `/dev`, `/proc` can't be reached. The sim's own Python is
   imported from a private folder before that, then taken out of `sys.modules`.
4. **Syntax errors** are reported by the real compiler, so their line is the board's (an unclosed bracket at the
   end of a file is reported on the line after it, as on the board).
5. ~~The build still has `js` and `jsffi`~~ — gone in the M2.2 rebuild (finding 6).
6. **`sys.settrace` is out of the build (M2.2); this reverses an M0 decision.** It made every Python *function
   call* ~30 times slower: 100 000 calls took 2.9 s (npm's settrace build: 18.5 s; without settrace: 0.1 s). M0
   timed only loops, so it didn't show. A Pico makes a call in ~3–5 µs, so with settrace the sim ran ordinary
   programs several times slower than the board (N-01). The line being run (screen 03) now comes from the chain
   of running frames that settrace kept anyway (`MICROLAB_FRAMES`; `microlab_frame_line/_file` in the patch),
   readable at every call into JavaScript and every VM hook — exact even during `time.sleep`, which the
   settrace hook could only get through its own frames. Rebuild checks: Stop and IRQs in busy loops (hook
   spike) and the GC spike give the same results as before; the `.wasm` is 577 KB.
7. **The VirtualClock** moves 10 µs per VM poll and per time reading (about one loop turn with a `ticks_ms()`
   call on a Pico), so `while ticks_diff(ticks_ms(), t0) < 1000` ends after ~100 000 turns, as on a board.
8. **Still the laptop's:** `time.time()` / `localtime()` (each board's own start date comes with its board
   module, M2.4–M2.6), and `asyncio`'s waiting (its `select.poll` wait uses real time, not the run's Clock —
   to route through `_ream` when a board slice needs asyncio).
9. **Each board's behaviour is copied from its port's C source** (`.cache/micropython-v1.29.0/ports/<port>/`,
   the version the sim runs): for the Pico W, `machine_pin.c` and `boards/RPI_PICO_W/pins.csv` — names,
   `repr`, constants, what `init()` changes, error texts. **To confirm in the golden recordings (slice 9):** the
   `repr` of a pin after reset (`Pin(GPIO15, mode=ALT, pull=PULL_DOWN, alt=31)`, from the RP2040's reset state)
   and of the LED (`Pin(EXT_GPIO0, mode=OUT)`); a PWM pin's `alt=` name (`PWM`, from `make-pins.py`).
10. **An exception in a soft IRQ handler** is printed and the program carries on: MicroPython's scheduler runs
    scheduled handlers protected (`py/scheduler.c`), on the boards as here. The console turns the `\r\n` of
    such "cooked" output into `\n`.
11. **Coverage of `src/python`.** MicroPython has no line-coverage tool without `settrace` (finding 6), so the
    board modules are covered by behaviour: every function a test list names has a test, and each slice's
    mutation checks show the tests notice a change. The ≥ 85 % gate is measured on `src/sim`.
12. **Busy-wait tests carry a time limit** (`while … and time.ticks_ms() < 5000`): a test program that never
    ends blocks the thread, so Vitest's timeout can't stop it — a broken timer hung the suite once. The worker's
    Stop (M2.8) will end such runs; the limit stays as a guard.
13. **The ESP32's firmware has a bug we copy:** `repr(Timer)` prints `mode=ONE_SHOT` for a periodic timer and the
    other way round (`machine_timer_print`: `repeat ? ONE_SHOT : PERIODIC`). The sim prints what the board prints.
14. **ESP32 estimates to confirm on a real board:** the ADC's full scale per attenuation (0.95, 1.25, 1.75, 3.1 V —
    the real ADC is not linear near its ends); TouchPad readings (600 untouched, 90 touched); the `repr` of an
    open-drain pin (`Pin.OUT`, because output-enable is checked first) and of a pin after reset (input, no pull —
    the strapping pins 0, 2, 5, 12, 15 have their own pulls at reset); whether IDF logs an error when a pull is
    set on GPIO 34–39 (the sim sets no pull, silently).
