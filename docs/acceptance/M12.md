## Modelling decisions (slice 1)

1. **Ctrl+C is a message, not a signal**: a reader thread in the runner gets it and interrupts the main thread, the same on macOS and Windows (where a child process has no Ctrl+C of its own, R12). What can't be interrupted (a C library that never returns) is ended by Stop after 0.5 s.
2. **Run sends the editor's text**, compiled under the file's name: an unsaved change runs as it is (Thonny's way), and a new file with no name runs in the user's Documents folder.
3. **A new Run is a new process**: the previous program's names and windows go with it, as IDLE's *Run Module* restarts its shell.
4. **The error's message is CPython's printed line**, with its hints (*Did you mean: 'print'?*) — `str(exc)` alone lacks them.
5. **The tests run on the computer's own Python** in development (3.14.5 here); the bundled 3.13 comes with the build's fetch step and is the one shipped.

## Modelling decisions (slice 2)

1. **One session per window**; Run, Restart and Ctrl+D start a new one, and the main process forwards only the current session's events — the one replaced ends quietly.
2. **A new file is `untitled.py`** with `print("Hello!")`, not marked unsaved until it is changed (IDLE's new window is empty and clean); it is saved in Documents/Python unless the student chooses elsewhere, and runs there until then.
3. **The shell is the simulator's console** (its prompt rules, history, Tab, Ctrl+C, Ctrl+D, the Plotter), named *Shell*; the runner's `>>>` is printed text, as MicroPython's is, so the same rules hold.
4. **The editor's themes** (Aa: Light, Dark, High contrast) apply to the Python 3 screen too: they were scoped to the workspace's code panel.

## Modelling decisions (slice 3)

1. **The window is the program's**, as IDLE's: no turtle drawn inside MicroLab — the real `turtle` and `tkinter`, all of them, with nothing to imitate. It is brought to the front when it opens.
2. **Closing the turtle window ends the program**, quietly: what a student does when the drawing is done is not an error.
3. **Tests never show a window** (the teacher's rule): with `MICROLAB_HIDDEN` the runner withdraws each one as it is made. Seeing the real window beside MicroLab is the gate's (manual) check.

## Modelling decisions (slice 4)

1. **MicroLab's own folder, not the computer's Python**: installing never changes a Python the school has, and needs no administrator; what is installed goes with MicroLab's user data, so a library installed once serves every program.
2. **Look up by name, not search**: PyPI offers no search to programs (only its website); a name typed, or one from the short list often used in class, is looked up on its JSON page.
3. **Removal by pip's own list** (`RECORD`), as `pip uninstall` would do, since pip can't uninstall from a target folder; a path in it that leads out of MicroLab's folder is never followed.
4. **Offline, a .whl file**: the classroom without internet installs a teacher's wheel with pip `--no-index` (its dependencies must be installed first, or in the same way).

## Modelling decisions (slice 6)

1. **A project is made before it is used**, as in PyCharm (the teacher): no untitled files to lose or scatter; a board project is saved where it was made from the start, so Save writes to it without asking (Save as still asks).
2. **The location starts at MicroLab's folder every time**: on the school's open computers (no sign-in) the last folder chosen is the previous student's; each student chooses their own folder — the dialog's tip says how.
3. **A Python project is a folder; a board project stays one `.mlab`** (its files are inside it, as they go to the board).
4. **Delete goes to the computer's Recycle Bin / Bin**, asked first: a student's mistake can be put back. Not exercised by the e2e tests (it would reach the computer's real Bin); the component tests cover it.
5. **A window may touch only the project it opened**, and nothing outside its folder (paths checked in the main process, as for Libraries).
6. **The shell's place and size are MicroLab's, not a project's**: remembered in its settings, the same for every project.
7. **Pairs in both editors**: the boards' editor gets them too — typing a closing bracket steps over the one made, so code typed in full comes out the same.

## Findings (slice 6)

1. **The e2e tests would have made projects in the computer's real `Documents`** (the app's Documents was the user's): with `MICROLAB_USER_DATA` set, Documents is now inside it. (Before Rev 11 a `Documents/Python` folder was made on demand; an empty one is on the development Mac.)
2. Testing Library's `waitFor` never ends under Vitest's fake timers: the tests' New project helper waits on promises only.
3. A test that makes several projects named them all *Test project*: the second was rightly refused. The e2e helper takes the next free name, as a student would.
4. A `.pyc` from a compile check was committed with 6a: removed, and `__pycache__/` is ignored.
5. A double-click on a file in a tree also selected its name's text: the tree's rows select no text.
6. *(Process)* One e2e run of 6a used the downloaded Python and Jedi — set aside before, but not that time. They are set aside for the assistant's runs since; the teacher runs the full suite.

## Modelling decisions (slice 5b)

1. **Jedi in a process of its own**, not in the runner: the program's process starts afresh at each Run and may be busy (a loop, `input()`); the editor's help must not wait for it, nor put Jedi on the student's path.
2. **Tab at `>>>` asks the program itself** (`rlcompleter`), not Jedi: the names that matter there are the ones the program made, with their real values — as in Python's own shell. Python's form is kept: `math.sqrt(`, `score()`, `while `.
3. **Jedi reads Python's modules from the Python it runs on** (the bundled 3.13 in the app) and MicroLab's libraries folder — the same as the student's program sees.
4. **The bundled Python and Jedi are fetched, not kept in git**: pinned versions, each checked by its SHA-256; M11's installers copy `vendor/python/<platform>-<arch>` and `vendor/python-tools` into the app's resources (where `findPython` and `findTools` look first).
